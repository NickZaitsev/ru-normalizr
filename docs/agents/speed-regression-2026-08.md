# Регрессия скорости, август 2026

Замеры от 18 августа 2026 года, локальный Windows-прогон, тот же станок и та же
`.venv`, что и у замеров из `docs/SPEED_OBSERVATIONS.md`.

## Как мерить сравнимо

Только через harness и только с прогревом — иначе цифры несравнимы с историей:

```
uv run python scripts/benchmark.py --real-only --mode tts --samples 3 --warmups 1   --prefix-chars 250000 --book benchmarks/corpus/03_karamzin_history_of_russian_state.txt
```

Свой самодельный таймер использовать нельзя: прогрев на первых 20 тыс. символов
вместо полного текста даёт заниженный результат (54 тыс. вместо 70 тыс. симв./с
на одном и том же коде), потому что LRU-кэш разбора слов остаётся холодным.

## Что из этого достоверно

1. **`126a979` («закрыть известные пробелы нормализации из E2E-корпуса») стоит
   около 24 %.** Замер повторён дважды по три сэмпла, разброс 3 %, знак
   устойчив: 102 тыс. до, 78 тыс. после. Коммит добавил правила согласования
   числительных, диапазонов, дат, дробей и составных единиц — искать нужно
   там, а не в более поздних коммитах.
2. **Откат трёх `perf(pipeline)`-коммитов стоил около 7 %** (108 тыс. → 101 тыс.).
   Причина откатов в сообщениях Revert'ов не указана.
3. **Остальные коммиты после 17 августа скорость почти не меняют.** Работа с
   усечёнными сокращениями (`483f54e`) стоит 1.3 % на реальной книге — она не
   виновата, хотя изначально подозревалась.

## Почему абсолютные цифры этого дня нельзя брать за истину

`.benchmarks/scale-4000000.json` фиксирует 19.94 с (200 645 симв./с) для
4-миллионного префикса на коммите `6cdd346` при `samples=1, warmups=0`. Тот же
коммит, те же параметры, 18 августа: **67.86 с, 58 944 симв./с — в 3.4 раза
медленнее при идентичном коде.**

Причина найдена и она внешняя: на станке шла сборка C++ (`siso` и около двадцати
процессов `clang-cl`), которая занимала примерно 40 из 60 ядро-секунд в
5-секундном окне, то есть 8 из 12 логических ядер. Пропускная способность
`normalize` однопоточная, поэтому конкуренция за ядра и память бьёт по ней
напрямую. CPU при этом не троттлил: AMD Ryzen 5 5600G держал 3901 МГц при плане
питания «Максимальная производительность».

Практические следствия:

1. **Абсолютные значения из таблицы выше занижены примерно в 3 раза** и не
   годятся для проверки целевого показателя. Перемерять нужно на свободной
   машине: `Get-Process | Sort-Object CPU -Descending | Select-Object -First 5`
   не должен показывать чужих потребителей.
2. **Относительные сравнения остаются в силе.** Все замеры делались подряд в
   одинаковых условиях, поэтому −24 % на `126a979` воспроизвелись дважды и знак
   устойчив. Именно так и нужно ловить регрессии: два коммита подряд, один
   станок, одна нагрузка.

## Целевой показатель

`AGENTS.md` требует не медленнее 180 000 симв./с. Сейчас 69 775 — цель не
выполняется в 2.6 раза. Порядок работ: сначала найти причину внутри `126a979`,
затем вернуть откаченные `perf(pipeline)`-правки, затем разбираться с
окружением.
