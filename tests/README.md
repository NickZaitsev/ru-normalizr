# Как устроены тесты

Набор большой, и почти каждый файл — таблица «фраза → ожидаемое чтение».
Поэтому важно не «где лежит проверка», а **зачем она лежит именно там**: от файла
зависит, что делать, когда проверка внезапно поменяла результат.

## Куда положить новый тест

| Файл | Что там лежит | Что делать при изменении результата |
| --- | --- | --- |
| `test_known_gaps.py` | Только **открытые** дефекты, каждый — `xfail(strict=True)` | Тест начал проходить (XPASS) → дефект закрыт: перенести кейс в `test_known_gap_fixes.py`, сняв метку |
| `test_known_gap_fixes.py` | Кейсы, снятые с закрытых пробелов, и корнер-кейсы правил, которые их закрыли | Упал → закрытый дефект вернулся, это регрессия |
| `test_regressions.py` | Все остальные регрессии, включая пришедшие из отчётов пользователей | Упал → регрессия |
| `test_e2e_corpus.py` | Плотные реалистичные фразы и современный корпус из `data/modern_normalization.json` | Упал → сломано взаимодействие стадий, а не одно правило |
| `test_case_rules.py` | По фразе на каждое правило выбора падежа числительного (`CASE_RULES`) — чтение и то, какое правило его решило | Упал → правило перестало срабатывать или его заслонил новый сосед сверху |
| `test_<стадия>_stage.py` | Юнит-тесты одной стадии, вызывают её функции напрямую | Упал → сломана сама стадия |
| остальные `test_*.py` | Один предмет на файл: единицы, морфология, опции, CLI, плейсхолдеры, скорость | — |

Новый дефект, который **не исправляется сейчас**, обязан немедленно получить
`xfail(strict=True)` в `test_known_gaps.py` полной реалистичной фразой — не
отдельным словом и не обрывком. Это требование [AGENTS.md](../AGENTS.md), и
именно оно делает `test_known_gaps.py` единственным реестром открытых дефектов:
второй список прозой уже расходился с ним молча, см. [docs/ISSUES.md](../docs/ISSUES.md).

## Таблицы кейсов в `test_known_gaps.py`

Кейсы разбиты на кортежи по происхождению: `HANDWRITTEN_GAP_CASES` — найденные
точечными проверками, `CORPUS_SWEEP_GAP_CASES` — прогоном по всему корпусу,
`BOOK_0N_GAP_CASES` — сплошным чтением конкретной книги из `benchmarks/corpus`,
`MODERN_CORPUS_GAP_CASES` — проверкой современного корпуса
(`data/modern_normalization.json`).
Пробелы одной книги обычно правятся и снимаются пачкой, поэтому разбиение
экономит время: видно, что именно принесло каждое чтение. Итоговый
`E2E_KNOWN_GAP_CASES` склеивает их все, тестовая функция одна.

## Современный корпус в JSON

Корпус книг — это дореформенная и историческая проза, поэтому современный
деловой, новостной, бытовой и технический язык проверяется отдельно:
[data/modern_normalization.json](data/modern_normalization.json) — 60 коротких
авторских абзацев по шести категориям (договоры, новости, рецепты, техника,
программное обеспечение, адреса и справочные ссылки). Ни персональных данных,
ни выгрузок из внешних систем в нём нет.

У каждого кейса есть `id`, `category`, `set`, `profile`, `source`, `expected` и
обязательный `reason` — почему выбрано именно такое чтение. Набор `dev`
использовался при разборе правил, `control` добавлен отдельно и держит другие
предложения: он показывает, что правила не подогнаны под первые семь абзацев
категории.

Ожидание вычитывается руками по [конвенциям чтения](../docs/agents/conventions.md),
а не снимается с нормализатора. Если абзац упирается в незакрытый дефект,
ожидание **не ослабляется**: дефект уходит в `test_known_gaps.py`
(`MODERN_CORPUS_GAP_CASES`), а абзац переформулируется так, чтобы проверять
работающее правило. Корпус прогоняется тестом `test_tts_modern_corpus` в
[test_e2e_corpus.py](test_e2e_corpus.py).

## Общие фикстуры

[conftest.py](conftest.py) даёт две фикстуры для E2E-таблиц:

- `tts(source) -> str` — нормализация профилем `NormalizeOptions.tts()`;
- `check_tts(source, expected)` — то же плюс сверка, и на расхождении печатается
  не diff двух абзацев, а конкретное разошедшееся слово с соседями слева.

Профиль по умолчанию (`normalize(source)` без опций) — **не** TTS, поэтому
проверки на нём оставлены как есть: подменять их фикстурой значило бы менять то,
что тест проверяет.

## Стиль

Новые тесты — pytest: `parametrize` с осмысленным `id` на кейс. Часть старых
файлов написана на `unittest` с `subTest` (`test_regressions.py`,
`test_year_stage.py`, `test_api.py` и другие); они переводятся на pytest по мере
правок, а не отдельным массовым перепечатыванием — механическая замена трёх сотен
`self.assertEqual` рискует незаметно ослабить проверку, ничего не давая взамен.

Тест без содержательного утверждения не нужен: проверка «мок вызвался» или
пересказ реализации хуже, чем отсутствие теста.

## Запуск

```bash
uv run pytest -q -m "not packaging"
```

Маркер `packaging` — сборка wheel через `python -m build`: она медленная и
требует сети, поэтому в CI запускается в одной ячейке матрицы. Локально её можно
прогнать отдельно:

```bash
uv run pytest -q -m packaging
```
